# Hindsight pg0 数据目录核验与开机自启修正（2026-11-02 实测）
适用：Windows，DSH profile `desktop`，`hindsight-api` + 内嵌 `pg0`（PostgreSQL 18.1），bank `dsh`。
关联既有文档：`09c331e0-b1df-4617-aca7-d5929f0f0260`（全量导入手册）、`208b79a6-873b-48ab-b03f-6a9c4b2db13c`（守护进程/硅基流动配置）。
本文只记录这两篇**未覆盖或被本次实测修正**的三件事：数据目录归属、pg0 自管理冲突、Startup 批处理写法。注意：导入手册第 2 节结尾「PG 需手工先起、不随系统启动」的表述已被本次实测推翻，以本文为准。

## 1. 先确认「活着的 postgres 到底用哪个 data 目录」，再谈删除

踩坑经过：导出导入时曾把 PG 整份拷到 `pgwork/`（`pginst` 161M + `pgdata`），随后改回用 `~/.pg0`。清理时按体积推断 `pgdata` 是旧残渣，实际它已从 68M 长到 **430M** —— 1430 条记忆全部写在这个副本里，而 `~/.pg0/instances/hindsight/data` 只有 68M 旧空数据。直接删除会丢掉全部导入结果。

判据（不要凭 `instance.json` 或体积猜）：

| 证据 | 命令/位置 | 结论 |
|---|---|---|
| 运行实例登记 | `~/.pg0/instances/hindsight/instance.json` 的 `data_dir` | **只是「登记」，不代表当前进程实际在用** |
| 真正数据目录 | 查 `postgres.exe` 命令行：`-D <path>` | 唯一权威依据 |
| 占用端口 | `netstat -ano | findstr :5432` → PID | 与上面 cmdline 的 PID 对齐 |

本次实测：`instance.json` 写的是 `C:\Users\13966\.pg0\instances\hindsight\data`，但 cmdline 是 `D:\DeepSeekHarness\pgwork\pginst\bin\postgres.exe -D D:/DeepSeekHarness/pgwork/pgdata -p 5432`，两者不一致才是真隐患。
规则：**任何「冗余副本」在删除前，必须先看 postgres 进程 `-D` 参数 + 目录体积/修改时间是否与最新写入吻合。**

## 2. 迁移回标准位置（已验证步骤）

1. 停 Hindsight（`taskkill`/服务停止），再 `pg_ctl stop` 停 PG，确认 5432 无监听。
2. 旧数据改名保留：`data` → `data.old-empty`（不直接删，留一次回滚点）。
3. `pgwork/pgdata` 整体移到 `~/.pg0/instances/hindsight/data`。
4. 从 `~/.pg0` 的安装目录用标准 data 路径启动 PG；`pg_ctl start` 可能**静默挂住不出输出**（本次前台 120s 无输出被转后台作业，但服务其实已起）——改为另开命令查端口与 `start.log` 判定，别只看 `pg_ctl` 的 stdout。
5. 启动 Hindsight 后 `/health` 应为 `healthy / database: connected`，再校验 bank：`total_documents: 1431`、`total_links: 191824`、`pending_operations: 0`、`failed_operations: 0`（节点数仍在后台增长属正常）。
6. 校验通过后再删 `pginst`（161M）与 `data.old-empty`。

## 3. 关键修正：自启脚本**不要**手工启动 PG

Hindsight 的 `pg0` 会**自己**启动内嵌 PostgreSQL（`memory_engine.start_pg0` → `pg0.ensure_running()`）。若启动脚本先手工起 PG，Hindsight 启动时会连续 5 次失败：

```
RuntimeError: Failed to start embedded PostgreSQL after 5 attempts.
Last error: Error: Instance already running (pid: 9212)
ERROR:    Application startup failed. Exiting.
```

现象容易误判：`hindsight-api.exe` 进程存在但内存仅 ~3.4M、8888 无监听、`daemon.out.log` 为空 —— 真正原因在 `daemon.out.log` 末尾的 pg0 异常。
正确链路：**Startup bat 只负责拉起 Hindsight；PG 交给 pg0 自管理。** 由 VBS 隐藏窗口调 `start.cmd`，`start.cmd` 仍是环境变量与启动 exe 的唯一真源。

## 4. Startup 批处理（`.bat`）的三个硬约束

1. **必须纯 ASCII**：以 UTF-8 写入的中文 `REM` 注释会被 cmd 按 GBK 解析 → 逐行报「不是内部或外部命令」/「文件名、目录名或卷标语法不正确」。校验：`file <bat>` 应显示 `ASCII text`。
2. **避开 `%DATE%` / `%TIME%`**：在括号块内与 `>>` 重定向同时出现时展开含空格/特殊字符，导致解析错乱。时间戳要么不加，要么用固定字符串。
3. **不要在脚本里依赖 `timeout /t`**：从 bash/作业环境测试 bat 时，`timeout` 会命中 GNU timeout（`invalid time interval '/t'`）。测试等待用调用侧 `sleep`，脚本内不要放 `timeout`。

## 5. 端到端自启验证配方（可复用）

1. 彻底停掉 Hindsight 与 PG，确认 5432 / 8888 均无监听。
2. 直接运行 Startup 下的 `hindsight-autostart.bat`（模拟登录触发），等约 40s。
3. 期望结果：
   - `/health` → `{"status":"healthy","database":"connected"}`
   - 5432 LISTENING 的 PID 是 **pg0 自己拉起的 postgres**（本次 PID 20316）
   - 8888 LISTENING
   - bank 校验 `docs 1431 / links 191824 / pending 0 / failed 0`
4. 自启日志 `%LOCALAPPDATA%\hindsight\autostart.log` 应出现 `launching Hindsight API (pg0 self-managed)` 与 `Hindsight launch dispatched`。

## 6. 遗留与后续

- `start.cmd` 内含硅基流动 API Key 明文，是唯一配置真源；Startup bat 里重复的一份环境变量实际会被 `start.cmd` 覆盖，属冗余，改模型/Key 只改 `start.cmd`。
- `pending_consolidation` 收尾时仍为数千（本次 ~5170 → 4949），是 background 二次提炼，不影响检索，别当成失败。
- `pgwork/` 只保留 `import_all.js` 等脚本，体积应降到 ~13K；若又出现上百 MB，先按第 1 节查是不是有第二个 PG 在写数据。

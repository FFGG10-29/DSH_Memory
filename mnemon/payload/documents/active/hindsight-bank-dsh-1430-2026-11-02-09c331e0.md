# Hindsight 全量记忆导入手册（bank `dsh`）

适用环境：Windows 桌面，DSH profile `desktop`，Mnemon `dsh-mnemon` 的 Hindsight 服务（`http://127.0.0.1:8888`）。
关联既有文档：`ade0758c-42fc-4ade-a26a-4cd95b513559`（Hindsight 守护进程）、`85bf0603-f2d9-4d02-bd11-bcee2aac0ba3`（MNEMON_DATA_DIR 跨工具对齐）。本文只记录这两篇未覆盖的**批量导入流程**。

## 1. 前置：Memory Body → bankId 映射

- DSH 的 `mnemon.json`（`version: 5`/`4`）在 `bodies[]` 里给出 body id（如 `hindsight-<uuid>`）与 `providerId: "hindsight"`。
- 真正的写入目标是 Hindsight 的 `connection.bankId`（本次为 `dsh`），不是 body id。先读配置确认 `bankId`，再发写请求。
- 已验证的写入口：`POST /v1/default/banks/{bankId}/memories`。

## 2. 关键阻塞：沙盒拦截内嵌 PostgreSQL 启动

Hindsight 依赖 PostgreSQL。本机没装系统级 PG，用的是 Hindsight 自带的 `pg0-embedded`（PostgreSQL 18.1.0，解压到 `~/.pg0`）。
DSH 沙盒开启时，postgres 启动自检报 `0xC0000142 / Permission denied`（沙盒拦住了它 spawn 的子进程）；关闭沙盒后立即启动成功，health 变为 `healthy / database: connected`。

结论：**Hindsight 起不来时先怀疑沙盒对子进程的限制，而不是 PG 数据损坏或端口占用。** 临时拷贝到 `pgwork/` 的 PG 副本（约 161MB + 68MB）在能用原生 `~/.pg0` 后即为冗余。

运行态注意：PG 是手工拉起的进程，**不随系统启动**。重启机器后 Hindsight 会再次不可用，需先起 PG 再起 Hindsight（或做成服务/写进 `start.cmd`）。

## 3. 同步 vs 异步写入

| 模式 | 请求体 | 实测代价 |
|---|---|---|
| 同步 | 直接 POST `items` | 2 条即消耗约 7,987 tokens；1430 条按此速率约需 6 小时 |
| 异步批量（推荐） | `items` + `async: true` + `operation_id`（**必须是合法 UUID**，自定义字符串会被 `value_error` 拒绝） | 30 条/批，47 批全部提交后由后台 consolidation 处理，总耗时约 1.5 小时 |

异步响应形如 `{"success":true,"bank_id":"dsh","items_count":20,"async":true,"operation_id":"<uuid>","usage":null}`。
批量测试先用 20 条探路，再看进度、再定正式批大小，是本次验证过的稳妥做法。

## 4. 进度监控与完成判据

- 用 bank 状态接口轮询 `nodes / docs / pending / failed`。健康的表现是 `failed` 恒为 0、`pending` 单调下降到 0。
- 注意两个**不同**的 pending 概念：
  - 请求级 `pending_operations`：0 表示所有提交已被接收并处理完；
  - `pending_consolidation`（本次收尾时 5170）：节点已落库，但二次提炼（碎片→高层 observation）仍在后台跑，不影响检索可用性。
- 完成标准看 `pending_operations: 0` + `failed_operations: 0`（本次 operations completed 102，长短不一，属正常）。

## 5. 本次结果基线（可作为下次对照）

| 指标 | 值 |
|---|---|
| 提交 | 1430 条，1 条 → 1 document，47 批异步 |
| 失败 | 0 |
| documents | 1431（多出的 1 个来自上线前 20 条测试批） |
| nodes | 5560（world 5318 / experience 57 / observation 185） |
| links | 191,824（semantic 99,544；temporal 91,348；entity 820；caused_by 112） |

原始 `metadata`（`original_id`、`importance`、`persona_id`）与时序时间戳（`storage_created_at`）原样保留，时序链才按真实聊天时间建立 —— 批量导入时不要为了省字节丢掉时间戳，否则 temporal 关联会失真。

## 6. 验证

导入后必须用一次 Mnemon Recall 做端到端召回验证（返回项应带 `memoryBodyName` = 目标 body 名、正确 `category` 与 `createdAt`），不要只看写入接口的 200。

## 7. 复现用脚本

`pgwork/import_all.js`（分页读取导出 JSON → 分批 submit → 轮询进度 → 打印 FINAL 汇总）。

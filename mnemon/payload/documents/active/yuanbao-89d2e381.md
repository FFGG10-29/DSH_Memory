# 元宝导出记录整理流程（已验证一次完整跑通）

来源：对一份 4.4MB / 51520 行的腾讯元宝聊天导出做全量提炼，最终 282 个会话 → 26 条记忆条目，分两个记忆空间入库。以下是与具体车型/项目内容无关、可复用的部分。

## 1. 为什么不能直接喂原文

元宝导出里 **约 90% 的文字是模型「思考过程」冗余**，用户真正说的话占比很小。因此提炼时的唯一输入应限定为用户发言行：

- 用户发言以 `### [我]` 为标记，只抽这些行。
- 其余一律丢弃，不要把「思考过程」当作用户主张写入记忆（否则会把模型自己的推理当成用户事实）。

## 2. 切分：先按真实边界拆成单会话文件

- 先用 node 脚本按真实分组头与 `## 会话` 边界切分，产出 282 个独立文件（约 2.19 万字符），放 `yb_extract/`。
- 同时生成 `yb_extract/_all_user_asks.txt`（仅用户提问汇总，约 7.8 万字 / 1467 行），这是给分析代理的实际输入。
- `yb_extract/_manifest.json` 保留完整索引，任何一批结论需要回溯原文时按编号定位，无需重跑切分。
- 切分而不是逐段读原文件，是为了让每个分析代理只吃自己主题的那几个小文件，避免上下文被冗余思考过程挤爆。

## 3. 提炼与写入

- 按主题分给多个分析代理（本次 6 个），每个代理只对分配到的会话文件做提炼，输出结构化条目（内容 + 分类 + 重要度）。
- 代理产出先写临时 JSON 文件再读回核对，不要让长结果只存在于子代理回复文本里。
- 由主代理统一去重、合并、裁决冲突后再落库；分空间入库（技术类 / 个人生活类各自独立空间），跨主题不混。
- 落库后必须做一次反向验证：用关键词检索能命中刚写入的条目，才认为写入生效。

## 4. 踩坑记录

### 4.1 子代理「completed without recording its result」
第一次批量写入的子代理返回 `Error: memory subagent completed without recording its result`，条目实际没有入库。处理方式是**原样重试一次**并核对回执；不要假定「代理说做完了」等于已写。批量写入应逐条检查返回体里的 `summary` / `memoryBodyIds` / `unembedded`。

### 4.2 临时文件路径不存在（C: 与 D: 混淆）
读回临时结果时路径报 `NOT_FOUND (os error 2)`，因为写入落在 `C:\Users\13966\DeepSeekHarness\tmp_mem_out.json`，而当前会话工作区是 `D:\DeepSeekHarness`，glob 实际命中 `D:\DeepSeekHarness\tmp_mem_out.json`。教训：**临时交换文件统一放会话工作区内用相对路径**，不要手拼用户目录或盘符。

### 4.3 每条都 unembedded
所有写入条目都返回 `unembedded`：向量服务未配置时，语义检索搜不到，但关键词、链接与最近性召回仍能命中。
- 这是环境配置问题，不是写入失败；回执里带 `memoryBodyId` 即已落库。
- 补齐方式：在 Mnemon 设置里配置 embedding（本次记录建议 bge-m3），再从 Test status 触发回填向量；该流程走 DSH 使用的 storage root 与 embedding 设置，终端里的 mnemon 命令可能两者都摸不到。
- 因此整理阶段的「写入成功」判据只能是关键词召回，不能依赖语义相似度结果。

### 4.4 跨来源冲突要分立案，不要擅自合并
同一批导出内不同来源（例如另一家模型的对话记录与本次导出）对同一事实给出互斥说法时，本次做法是**分别立案并标注待确认**，把待确认点交回用户裁决，而不是择优合并成一条。
同类做法也适用于明显的时间/数字歧义（例如代理把某个日期读错年份）：回到原文编号文件核对，按原文写法入库，并在汇报里明确请用户确认。

## 5. 可复用的定量经验
- 282 个会话 → 26 条条目；大量会话只是重复的技术问答，去重后真正新增信息密度很低。
- 「车型/工具询问」类会话产出的是参数矩阵，适合一次性合并成一条条目（引脚、报文 ID、线序、封装），不要拆成几十条碎片。
- 重要度应显式标注（importance 5 优先写），便于后续检索排序与容量管理。
